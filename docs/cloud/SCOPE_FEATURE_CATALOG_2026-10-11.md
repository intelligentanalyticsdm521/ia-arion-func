# Scope: the feature catalog (11 Oct 2026)

**Brandon's words:** "build the feature catalog properly" / "I would think we have a feature list and then a subscription tier list and those are synced up" / "build that product catalog properly via a sonnet or opus agent so we can go through the website builder and SEO software."

## 2. The build

### 2.1 Schema (platform-api migration `043_feature_catalog.sql`, TARGET DB iadm_platform, additive, re-run safe)
- `core.features` ADD `product_key NVARCHAR(32) NULL` (oliver | spark | arion | stella | argus | my_brand | forge | consulting; NULL = platform-level), `min_tier NVARCHAR(16) NULL` (lite | standard | pro | business; NULL = every tier of the product), `addon_key NVARCHAR(32) NULL` (seo | responder | leads_package | phone_line), `addon_min_tier NVARCHAR(16) NULL` (starter | essentials | growth | authority), `kind NVARCHAR(16) NOT NULL DEFAULT 'page'` (page | action | job | send | limit), `availability NVARCHAR(16) NOT NULL DEFAULT 'live'` (live | coming_soon | hidden), `group_name NVARCHAR(100) NULL`, `sort_order INT NOT NULL DEFAULT 0`, `updated_at DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()`; CHECK constraints on the enumerations; unique index on feature_key already exists (verify; add if not).
- The 156 February rows: `is_active = 0` (kept, never deleted). The one override row is left alone (its feature goes inactive, so it stops appearing).
- MERGE the seed (`db/seed/feature_catalog.json` -> generated `043` body or a sibling `043b` data migration): INSERT new keys, UPDATE changed columns, never delete. `core.service_features` gets one link per feature with a product (`is_enabled_by_default = 1`) so the February joins keep working.

### 2.2 Seed (`platform-api/db/seed/feature_catalog.json`, generated once by `scripts/_generate-feature-catalog-seed.mjs` from the sources in section 1, then hand-edited forever after)
- Pages: every `serviceCatalog.ts` key -> `{key, name: displayName, product: section mapped (ARION->arion, LUMEN->spark, OLIVER->oliver, STELLA->stella, ARGUS->argus, MY_BRAND->my_brand, FORGE->forge, CONSULTING->consulting, Shared->null), kind: page, availability: coming_soon when defaultStatus = coming_soon else live, group: the SubNav group title, sort: menu order, min_tier / addon / addon_min_tier: from the SubNav rule or ROUTE_ONLY_RULES (tierProduct my_brand -> product my_brand), hidden nav rows -> availability hidden}`.
- OLIVER actions: every `TIER_FEATURES` row -> `oliver_<key>` kind action (limits: `included_users`, `additional_seats`, `document_templates`, `active_job_limit` -> kind limit, no gate), min_tier = the lowest tier whose value is truthy (a qualifier string counts as included), group = the TIER_FEATURES group.
- The 24 `FEATURE_CATALOG` keys -> `my_brand_<key>` / `spark_<key>` kind action (where a page row with the same meaning exists, one row only: keep the page key and note the alias in the JSON `aliases`).
- SPARK segments and ARION path patterns do not create rows; they become the `ROUTE_FEATURES` maps in 2.4 pointing at page/action keys. Where a segment has no page (e.g. `sms`, `webhook-subscriptions`), add an action row (`spark_sms`, `spark_webhooks` exists as a page).
- Where the sources disagree, FEATURE_TIER_MATRIX_FULL.md section 13 wins, then 6, 7, 9, 10, 11, then 1-3. Every disagreement found is listed in the seed generator's output and in the scope's appendix.

### 2.3 platform-api
- `lib/featureCatalog.js` (a first draft exists, finish it): `loadFeatureCatalog(pool)` (60 s cache), `loadFeatureOverrides(pool, tenantId)`, `decideFeature(row, payload, overrides)` and `featuresFor(rows, payload, overrides)` (pure), `catalogVersion(rows)`.
- `resolveEntitlements` adds `features: featuresFor(...)`, `catalog_version`, and `sources.catalog` ("ok" | "unreadable"). `getEntitlements` caches as before.
- Routes: `GET /internal/feature-catalog` (internal token; the rows) and `GET /me/feature-catalog` (signed in). `POST /internal/entitlements/:id/invalidate` also clears the catalog cache.
- Semantics (the same everywhere): allowed true -> runs; allowed false -> refused with `reason` and `needs` ("needs SPARK Business"); allowed null -> a signed-in READ allows and logs, a SEND / cross-product WRITE / model SPEND holds. Overrides win. Platform-level (no product) is always allowed. forge/consulting (no node) allowed as before.
- Tests: executed with a fake pool: the decision table (owned/not owned/tier below/add-on missing/SEO rung/override on/override off/undecided/platform-level/no node), the payload carries `features`, the routes answer, the seed loads (every row valid: enumerations, product keys, no duplicate keys, every page key from serviceCatalog.ts present), and a mutation per guard.

### 2.4 The four APIs (LUMEN+STELLA surfaces, OLIVER, ARION + arion-func)
- Each gets ONE `requireFeature(key)` middleware (reads `payload.features[key]` through the repo's existing entitlements client; 403 `{error:'feature_not_in_plan', feature, needs, message}` on false; allow + log on null for reads; the key missing from the payload = catalog mismatch -> log at error, allow a read, hold a send).
- The path maps become `ROUTE_FEATURES` (pattern -> feature key) read by the existing mounted middleware, so every tiered route is covered without touching hundreds of files; routes added later declare `requireFeature` directly. The old `FEATURE_MIN_TIER`, `PATH_MIN_TIER`, `tierGate(tier)` call sites and `TIER_FEATURES` tier lookups are deleted or reduced to views of the payload (replace means delete). oliver `tierLimits`/`TIER_CAPS` numbers stay (limits are not this build).
- Timers, sends and model spends that today ask "product owned" keep that check and add the feature key where the catalog has one (e.g. `oliver_recurring_auto_schedule`, `spark_sms`, `my_brand_voice_monitor`).
- A startup check per app: fetch `/internal/feature-catalog` once, log every key in `ROUTE_FEATURES` / `requireFeature` calls that the catalog does not have. A test per repo pins that every key named in the repo appears in the repo's own `test/fixtures/feature-keys.json`, and platform-api's `scripts/_check-feature-keys.mjs` (dev tool) diffs those fixture files against the seed.

### 2.5 Portal
- `navVisibility.ts`: `isEntitled(key, ctx)` reads `ctx.features[key]` (from `/me/entitlements`); `minTier`, `addon`, `addonTier`, `tierProduct`, `everyTier` and `ROUTE_ONLY_RULES` are deleted. `hidden` becomes `availability: hidden` from the catalog; `coming_soon` likewise. The lock label uses `needs`.
- `serviceCatalog.ts` keeps key, displayName, section, route, description; `defaultStatus` is deleted; `buildEnabledServices` branches are deleted; `enabledServices` = keys with `allowed !== false` and availability live.
- `productAccess.ts` unchanged (product-level "not in your plan" screen). FeatureLocked / PlanWall read `needs`.
- One test: every `serviceCatalog.ts` key and every SubNav key exists in `test/fixtures/feature-keys.json` (the Portal's copy of the seed keys).

### 2.6 Release order
1. platform-api: migration 043 dry run against production with `scripts/run-pipeline-migrations.js --dry-run`, then push (the pipeline migrates first, then deploys). Verify `GET /internal/entitlements/<IA>` carries `features` with a count equal to the seed.
2. The four APIs (any order), then the Portal. Each proven by /health commit and one read per repo (a 403 from `requireFeature` on a known-locked feature for Briarwood, through the deployed API, with the internal token and a real business id, no email sent).
3. Click-through in the pane of three locked rows and one unlocked row per product (Brandon signed in).
